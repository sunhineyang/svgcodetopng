# SVGCodeToPNG 未来迭代 Feature List 规划执行方案

## Summary

本次任务的目标不是直接改代码，而是基于当前仓库真实现状，产出一份“混合版”规划文档：

- 上半部分是产品路线图式的 Feature List，总结未来最值得做的能力方向与优先级逻辑。
- 下半部分是核心 Feature 的轻量 PRD，写清楚做什么、为什么做、用户怎么用、怎么判断是否有效。
- 规划不按季度或版本拆分，而是做一份完整的 feature list，总体围绕 `svgcodetopng` 这个核心心智展开。
- 优先级判断同时服务三件事：导出转化、SEO 流量、产品壁垒。

最终交付物建议为一个新的独立规划文档，不覆盖现有旧 PRD，避免把历史内容和新战略混在一起。

## Current State Analysis

以下结论均来自当前仓库实际代码，而不是假设：

### 1. 当前产品核心能力已经不弱，但“导出能力最强”这件事还没真正建立起来

- `components/CodeToPngConverter.tsx`
  - 已有 SVG / HTML 两种输入模式。
  - 已支持 PNG / JPG / GIF / WebP / PDF 导出。
  - 已支持质量、尺寸、背景色、缩放、预览后下载。
  - 已有颜色提取与颜色替换能力。
- 这说明产品已经不是“只能转 PNG 的极简工具”，而是一个功能不算少的在线转换器。
- 但导出底层目前仍主要依赖浏览器里的 `Image + Canvas + html2canvas + gif.js + jsPDF` 管线，还没有看到：
  - 更高质量的 SVG 渲染引擎抽象；
  - 导出质量预设；
  - 一键多尺寸/多版本导出；
  - 导出前自动诊断与修复；
  - 针对 Figma 脏 SVG 的专门处理链路。

### 2. AI 与编辑能力已经存在，但还没有完全变成“服务导出”的产品结构

- `components/AiAssistant.tsx`
- `hooks/useAiSvgAssistant.ts`
- `utils/ai-svg/constants.ts`

当前 AI 已支持：

- 优化代码；
- 修改颜色；
- 改尺寸；
- 加动画；
- 加阴影；
- 调整布局。

这说明“AI 帮用户改 SVG”已经成立。
但从现有结构看，AI 更像一个并列功能模块，而不是紧贴导出流程的“导出前助手”。也就是说，用户还没有被清晰引导到：

- 先检查 SVG 是否适合导出；
- 再自动清理；
- 再选择质量预设；
- 再导出多个目标结果。

### 3. 当前仓库里没有看到真正落地的浏览器端 SVG 优化引擎和高质量渲染引擎

- `package.json`

当前依赖里没有看到已接入的：

- `svgo` / `svgo/browser`
- `resvg-wasm`
- `@svgr/*` 或同类 React 组件转换方案

这意味着你前面调研里提到的几条关键能力，目前大概率仍停留在“方向正确，但尚未产品化”的状态：

- 导出前智能优化；
- 高质量渲染提升；
- 生产导出（React 组件、干净 SVG）；
- 变体导出。

### 4. 当前产品内容定位和真实产品能力之间存在偏差

- `messages/en.json`
- `.trae/documents/svgcodetopng-product-requirements.md`

当前文案和旧 PRD 里仍大量强调：

- 模板库；
- 定价；
- 注册用户 / 高级用户；
- 1000+ 模板；
- 更宽泛的 AI 设计能力。

但从仓库现状看，这些内容有些是弱化状态，有些并未形成真正的产品主轴。反过来，最接近真实价值的“导出体验、导出质量、导出前优化、开发者生产导出”反而还没有被完整提炼成新的规划主线。

### 5. 当前还存在一个与产品全局定位相关的历史问题，需要在规划文档里明确标注，但不在本轮直接处理

- `app/page.tsx`

当前根路由仍然重定向到 `/en`。这和你强调的“默认语言就是英语，不应该有 `/en` 默认后缀”不一致。

这个问题会影响：

- SEO URL 策略；
- 默认语言心智；
- 未来关键词页与产品页的规划方式。

但本次任务是先做 feature list 规划，所以这里只把它列为“影响规划的现实约束”，不把它混进本轮主交付里。

## Proposed Changes

### 1. 新增一份独立的未来迭代规划文档

目标文件：

- `.trae/documents/svgcodetopng-future-feature-list.md`

做法：

- 新建一份全新的规划文档，不改旧 PRD。
- 用“导出驱动”作为唯一主线，把所有 feature 放进统一的判断框架里。
- 文档结构采用“路线图 + 轻量 PRD”混合形式。

原因：

- 旧 PRD 更像早期愿景稿，和当前实际产品已有偏差。
- 新文档独立存在，便于后续逐条落地，不会把历史内容污染到新的判断体系。

### 2. 在新文档开头先写清楚产品北极星与优先级判断公式

涉及内容来源：

- `config/site.ts`
- `package.json`
- `components/CodeToPngConverter.tsx`

做法：

- 明确产品核心心智是：`svgcodetopng = 把 SVG 更方便、更高质量、更专业地导出成图片`
- 明确 feature 入选标准：
  - 是否直接提升导出成功率；
  - 是否直接提升导出结果质量；
  - 是否直接减少导出前的手工处理；
  - 是否能带来新的关键词覆盖和转化场景；
  - 是否能形成比普通在线转换器更强的能力壁垒。

原因：

- 如果没有统一判断公式，feature list 很容易重新散掉，回到“AI、模板、优化、导出并列”的旧思路。

### 3. 用真实现状做一页“当前能力 vs 缺口”的盘点

参考文件：

- `components/CodeToPngConverter.tsx`
- `components/AiAssistant.tsx`
- `hooks/useAiSvgAssistant.ts`
- `utils/svg-color.ts`
- `package.json`

做法：

- 把现有能力分成 4 类：
  - 已具备；
  - 已有雏形但没产品化；
  - 用户高频需要但当前缺失；
  - 不应优先投入。
- 明确哪些方向“看起来强，但不该排前面”：
  - 批量处理；
  - 重模板内容平台；
  - 过重的通用 AI 设计工具化。

原因：

- 这样后面的 feature 优先级更容易让团队接受，也能避免重复讨论。

### 4. 输出完整 Feature List，并按“导出闭环”而不是“开发模块”来分组

目标文档中的核心章节建议如下：

- A. 导出质量能力
- B. 导出便捷能力
- C. 导出前智能优化
- D. 高级导出 / 生产导出
- E. SEO 与转化增强能力
- F. 暂不优先能力

每个 feature 都统一写 6 个字段：

- Feature 名称
- 用户痛点
- 用户价值
- 为什么现在值得做
- 对 SEO / 转化 / 壁垒的影响
- 建议优先级

原因：

- 这是最适合你当前目标的写法：不是单纯技术排单，而是围绕增长与产品价值一起判断。

### 5. 明确 Feature List 的推荐主排序

建议在最终文档里采用下面这套主排序逻辑：

- P0：直接让“导出更清晰、更方便、更稳”的能力
- P1：让“导出结果更专业、更适合开发/设计工作流”的能力
- P2：增强分发、SEO 覆盖、品牌感知的能力
- Not Now：不直接强化导出闭环、或投入产出不够高的能力

基于当前仓库现状，文档应默认把下面这些放进最高优先级候选：

- 高质量导出引擎 + 质量预设
- 便捷导出预设 + 一键多尺寸/多格式
- 导出前智能优化
- 导出错误诊断与修复建议

接着是第二层：

- Variant 快速导出
- React 组件导出 + 干净 SVG
- Figma SVG 专项清理

第三层再放：

- 关键词页驱动的场景化 feature 包装
- 导出工作流提示与转化组件
- 结果页推荐与交叉销售

### 6. 为核心 Feature 补上轻量 PRD

建议只给前 5-8 个最关键 feature 写轻量 PRD，避免文档太空或太散。

每个 PRD 小节包含：

- 目标用户
- 触发场景
- 核心交互
- 输入 / 输出
- 边界情况
- 成功指标

重点优先写这些：

- 高质量导出引擎 + 质量预设
- 一键导出预设
- 导出前智能优化
- Variant 快速导出
- React 组件 / 干净 SVG 导出
- Figma SVG 清理入口

### 7. 在文档末尾单独加一节“关键词、竞品、转化路径如何映射到 Feature”

这部分不是重复调研，而是把调研结论变成产品动作。

建议拆成三张表：

- 关键词机会表
  - 核心词
  - 长尾词
  - 高意图场景词
- 竞品差异表
  - 普通转换器
  - SVG 优化工具
  - React SVG 工具
  - 高质量渲染工具
- 转化路径表
  - 落地页进入
  - 粘贴 SVG
  - 预检查 / 优化
  - 预览
  - 导出
  - 二次推荐

原因：

- 这样这份 feature list 才不只是“想法清单”，而是能直接指导后续产品、SEO、页面改版、功能排期。

## Assumptions & Decisions

- 决定 1：本次交付重点是“未来迭代 feature list 规划”，不是立刻实现功能。
- 决定 2：输出采用“路线图 + 轻量 PRD”的混合形式。
- 决定 3：不按时间排路线图，而按“产品重要性”排优先级。
- 决定 4：优先级同时考虑三件事：SEO 流量、用户转化、产品壁垒，但默认以“导出闭环”优先。
- 决定 5：不修改现有旧 PRD，避免历史定位和新定位相互污染。
- 决定 6：默认不把批量处理作为本轮重点。
- 决定 7：默认把 AI、优化、React 导出等能力都定义为“服务导出”的二级能力，而不是与导出并列的一等主轴。
- 假设 1：你接下来希望我在计划获批后，直接产出完整的 feature list 正式文档，而不是先做更长的竞品补充研究。
- 假设 2：本轮文档允许指出当前产品定位与仓库现实之间的不一致点，但不会在这一步直接修改产品文案或代码。

## Verification Steps

计划执行时，按下面标准验证产出是否合格：

1. 检查最终文档是否基于真实仓库现状，而不是只复述外部调研。
2. 检查每个 P0 / P1 feature 是否都能回答同一个问题：
   - 它是否让 SVG 导出更方便、更强、更清晰？
3. 检查文档是否同时覆盖三类价值：
   - SEO 获取流量；
   - 提升导出转化；
   - 建立差异化壁垒。
4. 检查是否把“不该优先做”的方向明确写出来，避免后续反复摇摆。
5. 检查轻量 PRD 是否足够具体，能让下一步继续细化为执行需求。
6. 检查文档中所有对“当前能力”的判断，都能在以下文件中找到依据：
   - `components/CodeToPngConverter.tsx`
   - `components/AiAssistant.tsx`
   - `hooks/useAiSvgAssistant.ts`
   - `utils/svg-color.ts`
   - `package.json`
   - `messages/en.json`
   - `app/page.tsx`
